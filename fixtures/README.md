# Synthetic geographic evidence — format 1

**Slice 2: Awaiting acceptance.** These are portable, entirely invented inputs and
manually specified expectations, not published Platform products. No owner GPS,
activity exports, credentials, national datasets or network calls are used.

Run the **complete suite** from the repository root with Python 3.9 or newer:

```sh
python3 -m unittest discover -s tests -v
```

For fixture counts and the direct audit alone:

```sh
python3 scripts/validate_fixtures.py
```

Python's standard library supplies JSON, mathematics and unittest with no package
installation. It is audit tooling only and implies no application language,
framework, map provider, production API or physical data-contract choice.

## Common envelope and fields

Every JSON file has `format_version: 1`, `family`, `synthetic: true`, and `cases`.
Each case has the following fields (required even for partial cases):

| Field | Meaning |
| --- | --- |
| `id` | Stable lowercase local identifier; combine with family for global identity |
| `description` | Behaviour being illustrated |
| `basis` | `accepted_policy`, `mathematical`, or `provisional_convention` |
| `status` | `resolved` for explicit outcomes under the stated basis; `partial` when a named question remains |
| `input` | Synthetic evidence, geometry or preassigned Platform-like tile events |
| `expected` | Authored outcomes, never generated by a production algorithm |
| `unresolved` | Nonempty questions for partial cases; empty for resolved cases |

`resolved` does **not** mean empirically VeloViewer verified. A provisional
convention is local to these fixtures and is not an accepted Platform policy.
Partial cases retain any independent resolved fields. `null` in an expected field
means not asserted (or, for `new_square_milestone`, no new event); zero and empty
lists are explicit results. Read the case question rather than treating null as
zero. Expected keys are intentionally family-specific, not a speculative shared
product schema.

All coordinates use `[longitude, latitude]` in degrees unless explicitly labelled
toy units; all tile references use `[z, x, y]`. Rectangles use west/south/east/north.
Local tile offsets are added to `anchor_tile` x/y, with y increasing southward.
Tile sets have no implied geographic size in square kilometres. Zoom-14 Web
Mercator tiles are not constant-area 1 km² cells.

Samples contain synthetic `activity_id`, zero-based `sample_index`, UTC timestamp,
coordinate (or null), supplied `qualification`, `policy_version` and `resolution`.
States are `accepted`, `rejected`, `uncertain`; only accepted full-resolution
samples establish visits. No qualification threshold is inferred. `syn-q1` and
`syn-q2` are labels, not numerical quality policies. Activity identity and absolute
times are supplied, not derived from any real source identifier or elapsed stream.
Segments reference **array positions in the containing samples list** using
`from_sample`/`to_sample`; these are distinct from per-activity sample indexes.
Each segment independently carries its supplied qualification/policy.

## Family semantics and inspection certificates

### Tile geometry

The candidate grid is zoom 14, n = 16,384. For longitude L and latitude P:

- projected x = `(L + 180) / 360 * n`;
- projected y = `(1 - asinh(tan(P * pi / 180)) / pi) / 2 * n`;
- tile ownership floors projected x/y; inverse edges use
  `atan(sinh(pi * (1 - 2*y/n))) * 180/pi`.

The fixture convention includes west/north edges and excludes east/south edges.
Thus a shared edge belongs to its east/south neighbour. Longitude +180 aliases
-180; longitude outside [-180,180] is rejected, not silently wrapped. Supported
latitude is `(-85.0511287798066, +85.0511287798066]`; the exact southern limit is
excluded under the half-open grid. Polar and nonnumeric/missing inputs are errors.
These seam/limit choices require Platform agreement and external validation.

JSON decimals are read as binary64 without six-decimal rounding. For these
**test audits only**, projected values within 1e-9 tile units of an integer snap
to that integer before flooring (about 2.2e-11 longitude degrees). This accounts
for inverse-edge decimal representation error; it is not a GPS acceptance buffer.
Inside/outside cases use 1e-7-degree displacements, well beyond that tolerance.
Bounds/centres use 1e-12-degree audit tolerance. Exact origin and dyadic longitude
edges plus hand-specified inverse-latitude constants anchor independent checks.
The test formula does not author or rewrite the expected constants.

`tile-reference` supplies all neighbours and the projected centre, **not** the
arithmetic mean of edge latitudes. `deliberate_invalid` cases declare expected
errors explicitly. JSON disallows non-finite numbers; the string `"NaN"` tests
nonnumeric input without nonstandard JSON. Error labels are fixture vocabulary,
not future API requirements. No wraparound cluster adjacency policy is implied.

### Visit evidence and arrangements

`positive_visit_evidence: false` and `evidence_state: insufficient` mean that these
inputs do not establish a visit, not a universal claim that the tile was never
visited. Segment/corner-only crossings have accepted endpoints outside the target
and still cannot tick it. Repeated samples in one activity count once.

Each arrangement lists every visited offset and **all** largest-square origins.
A square extends side cells east and south from its origin. Keeping all tied
origins avoids selecting a canonical tie winner. Generic four-neighbour component
counts, interior (all four neighbours visited) and boundary lists are mathematical
certificates only: none is asserted to be VeloViewer cluster membership. For
example a 2x2 has a side-2 square but no four-neighbour interior; the cross has
one interior tile but only side-1 squares. A one-wide bridge joins generic
components without proving a VeloViewer cluster connection. All VeloViewer cluster
outputs remain null with explicit questions; no current classification is used
to infer historical cluster membership.

### Historical states

History consumes **preassigned accepted tile visit events**, not fabricated raw
GPS conversion. Each event supplies activity/sample/time/policy/resolution
provenance and tile offset. These are fixture inputs for a future Platform
checkpoint conformance test or Explorer replay; they do not assert a published
Platform contract. Activity order is explicit; timestamp ties/order policies
remain future Platform work. Each `ordered-growth` checkpoint includes the full
historical set, count and square size, even the unchanged activity. Counts are
1, 1, 2, 5, 10; square sides 1, 1, 1, 2, 3. The isolated tile remains outside the
square. Cluster counts remain unresolved.

`backfill` inserts syn-h0 before syn-h1 and makes it first recorded origin visit;
syn-h2 remains last, with three distinct activities visiting the origin. The final
set stays unchanged. `invalidation` starts from q1 and under q2 rejects **all**
syn-h5 visit evidence; its earlier 2x2 state survives, the final count becomes 5,
and milestone 3 disappears. Retain old q1 snapshots, do not mutate them. Compare
against the explicit base-case key. `skipped-square-size` goes directly from side
1 to 3 at activity boundaries: only 1 and 3 are milestone events, not 2.

### Coverage and countries

Coverage's same equatorial support is an **abstract named span**, not a selected
spatial bin. `once`, `dense` and `repeated` each have one distinct activity;
`two-activities` has two despite differing raw sample counts. Segment indexes and
forbidden connections state which supplied evidence could support later coverage.
Missing/rejected observations break connections. Accepted samples do not upgrade
an uncertain/rejected segment. Null coverage counts in gap/uncertain cases defer
aggregation geometry; no heatmap aggregator, resolution or weighting is supplied.

Countries are invented adjacent unit rectangles. Border ownership is deliberately
unresolved. Presence uses only accepted samples, with no minimum-distance rule.
A first visit references the determining sample; repeated visits keep the first.
Toy segments have supplied length **12 arbitrary units** with linear planar
allocation, not metres or geodesic length. The symmetric cross-border segment
allocates 6 to each country. The through-no-sample segment allocates 4 to each,
leaves 4 unallocated, and establishes **no** country visit. The uncertain segment
allocates zero and keeps all 12 uncertain, while its accepted endpoint samples
still establish presence. These fractions explain conservation without choosing
a production distance model or boundary worldview.

### Ride Finder

Inputs expressly supply completeness. `complete_for_predicate` is a synthetic
assumption, not a proposed method of proving real route completeness. Conditional
starts/ends examples treat the supplied point as the known exact endpoint.
Conditional traverses examples use accepted segment intersection; canonical
composition and endpoint windows remain open questions in separate partial
cases. Their numeric expected results are useful only under those assumptions.

`sample_presence` and `segment_intersection` remain separate facts. A crossing
segment with both samples outside can have false sample presence and true segment
intersection. True evidence is possible in an incomplete route; absent positive
evidence in an incomplete route is unknown, not confirmed false. Radius examples
use an exact centre point in a toy planar area and select no real distance model.
All shapes avoid ambiguous border touches except explicitly unresolved examples.

| value | NOT value |
| --- | --- |
| true | false |
| false | true |
| unknown | unknown |

This is also machine-readable as `ride_finder/negation-table`. Every applicable
case includes both a result and its negation. Neither NOT unknown nor lack of GPS
creates a confirmed match.

## What validation establishes

| Level | Current evidence |
| --- | --- |
| Structural audit | Required common and family outcome fields, IDs, supported labels, coordinate/tile ranges, timestamps, sample uniqueness, segment and base-case references, synthetic provenance, declared unresolved states |
| Independent expectation audit | Fixed forward conversion and inverse centre/bounds, neighbours, exhaustive tiny-set square certificates/ties, generic connectivity/interior certificates, cumulative history counts/milestones, distinct-activity versus sample counts, segment exclusion, distance conservation and NOT table |
| Future algorithm conformance | **Not run.** No Platform or Explorer geographic implementation is under test; country polygon intersections, visit assignments, full historical rebuilds, Ride Finder geometry and production completeness need independent future consumers |
| External compatibility | **Not verified.** Public documentation is evidence of stated behaviour, not empirical output from a VeloViewer account |

Tests are mutation-based as well as positive: duplicate/missing IDs/fields,
invalid states/provenance/time/coordinates, dangling segments/references,
fabricated square ties/history/milestones, broken distance conservation and
unknown-negation errors must be rejected. The validator is intentionally small,
not a general JSON Schema engine, query service, geometry library, exhaustive
fuzzer or credential scanner. In particular it does not prove every hand-authored
country or Ride Finder result; the simple geometry and explanations are human
inspection certificates until independent algorithm conformance tests exist.

There are no generated geographic assets to reproduce. JSON files are the durable
source; never regenerate expected results from the algorithm under test. Temporary
authoring scripts are not dependencies. Validation neither writes nor fetches data.

## Reuse without moving canonical ownership

Platform tests can read JSON in R, Python or another tool, map synthetic identities
and supplied states into a test adapter, run their **own** implementation, then
compare only the resolved fields under agreed conventions. Pin the Explorer
commit/format and qualification/reference versions; keep all tied square origins
until a tie policy is accepted. Do not depend on Python audit functions as a
production calculation library. First agree or exclude provisional policies.

Explorer tests can instead inject the expected products/checkpoints to test tile
inspection, square outlines, historical navigation, skip-unchanged behaviour and
unknown-result display without calculating canonical geography. Partial/null
fields must stay visibly unknown. Neither consumer should treat the fixture
vocabulary as an accepted physical interface or silently convert unresolved
cluster/completeness policy into an implementation default.
